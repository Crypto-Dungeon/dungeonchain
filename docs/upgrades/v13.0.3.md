# Dungeon v13.0.3: CryptoDungeon validator management recovery

Release preparation only. No activation height is assigned, and this change is
not proposal 45. The review candidate is `13.0.3-rc.1`; it must not be installed
as a live replacement before a separately approved activation height.

## Purpose and scope

The compromised CryptoDungeon operator account remains frozen. This upgrade
restores narrowly scoped management through the existing clean recovery wallet
`dungeon10cr0mweqjyz856kyyy03yzj6av3vmy0p0653lh`. It preserves the validator
identity `dungeonvaloper1aj5jlmvqp8dd26rsec6624szthlazdn25leye3`, consensus key,
bonding/jailing state, stake, third-party delegations, accrued rewards and funds.

At activation the handler validates both account public keys, the validator
binding, the current rotated consensus key and withdrawal destination. It
atomically removes authorizations issued by the old operator, redirects its
withdrawal destination to the recovery wallet, and creates the scoped SDK grants.
It does not automatically transfer funds or withdraw rewards.

The clean controller can use a top-level SDK `MsgExec` for voting, validator
metadata, ordinary staking management, unjailing, commission/reward withdrawals
and future consensus-key rotation. Existing SDK restrictions still apply,
including rotation timing, balances, fees and validator status. Bank sends and
withdrawal destinations are restricted to the same recovery wallet. Contract
execution, granting/subdelegating old-operator authority, other frozen accounts,
old-key direct signatures, old fee granters and nested recovery are excluded.

The ante gate issues single-use consent for the exact top-level request. The
registered authz service checks that consent again at execution, requires the
ordinary SDK grant, and atomically executes the batch. A runtime contract call
cannot manufacture or reuse that consent. No new protobuf message type, store,
module consensus version or account public-key substitution is introduced.

## Plan and sequencing

- Exact plan name: `v13-cryptodungeon-operator`.
- Required prior completed plan: `v13-contract-roles`, at an earlier height.
- Proposal 45 schedules that prior plan at height **22,500,000**, subject to its
  voting outcome. This release does not change that proposal or v13.0.2.
- Choose the new height only after accounting for the prior upgrade, a separate
  governance vote and validator preparation. Do not submit a competing plan:
  the SDK stores one pending software-upgrade plan.

Keep the current approved binary running until its scheduled handoff. The SDK
intentionally rejects a binary containing the pending handler when run ahead
of the activation height. Stage the binary under Cosmovisor's exact plan name;
do not switch early, roll back a live node, or copy any signing key between hosts.

## Validation and operator handoff

The preparation includes the application/repository tests and a disposable
mainnet-state rehearsal anchored to height 22,368,768 and app hash
`3FC48346799264FA7D38F83DF2B93D8E7D79BA7B012D0D1B71AA4AE0104D7862`.
The harness restores only the retained canonical version of its explicitly
marked copy, replays the original recovery including its queued rotation delay,
and exercises both scheduled handlers through `FinalizeBlock` and `Commit`.
Rehearsal heights are synthetic; they are not proposed mainnet heights.
No node is started, no private/signing files are loaded and nothing is broadcast.

The same harness compares every unrelated module's raw key/value fingerprint,
checks distribution changes at the withdrawal-address key only, and runs full
SDK management and voting simulations. Simulation skips cryptographic signing
by design; wallet possession is verified separately with a fresh ADR-36 proof.
See the dated preparation report for actual test results, artifact checksums,
source commits and limitations. This is an engineering review, not an external
security-audit certification.

Before final publication, verify the exact current operator/controller public
keys, validator consensus key, withdrawal address and old-operator grants again.
Before activation, verify the prior upgrade's completed-height record and the
approved new plan. Validators should review the source diff, binary provenance,
checksums and state-rehearsal evidence independently.

After activation verify the completion marker, new withdrawal destination,
scoped grants, unchanged validator record and continued rejection of the old
signer. Management uses the clean wallet and SDK authz; the old wallet profile
does not become usable. For example, the clean signing device can construct the
desired operator message and run `dungeond tx authz exec <unsigned-tx-file>` with
the clean controller selected. Never import the recovery private key on a
validator server just to manage the validator. Preserve uint64 account numbers
exactly in client tooling; do not cast them to JavaScript floating-point numbers.
