# Dungeon v12 — full Cosmos SDK55 migration candidate

Status: draft software candidate. No production height, governance proposal,
validator-key change, mainnet deployment or published release is part of this PR.
The plan name is **v12**, whether upgrading directly from v10 or from the separate
v11 compatibility candidate. Do not use this binary for the v11 plan.

## Stack and behavior

| Component | Live v10 | Candidate v12 |
| --- | --- | --- |
| Cosmos SDK | 0.53.7 | 0.55.0 |
| CometBFT | 0.38.21 dependency | 0.40.0 |
| IBC | 10.7.0 | 11.2.0 |
| wasmd | 0.60.9 | 0.70.4, local SDK55 compatibility port |
| WasmVM | patched 2.3.5 | patched 3.0.8 |
| Go release builder | 1.25 for baseline | 1.27.1 |

SDK54 and SDK55 constructor, store/v2, log/v2, CLI and module migrations are
applied together. The application adds the mandatory key-rotation fee burner
account and the SDK55 bank end-blocker. It supports ML-DSA-65 account signing,
validator consensus-key rotation, and verification of ML-DSA IBC headers.
IBC classic transfer/ICA/Wasm routes remain; IBC v2 transfer and Wasm routes
are registered. The maintained PFM and rate-limit modules now come from IBC11.
The transfer stack sends through PFM, then rate limiting, then the channel
keeper; forwarded transfers cannot bypass quotas.

The v12 handler runs registered migrations and refuses a changed staking
bond denom, commission floor, consensus-key allowance or global fee policy.
The live 5% commission floor and `udgn` denom remain. A new rotation fee defaults
to 1,000,000 bond-denom units (1 DGN on dungeon-1) and is burned; governance can
subsequently update the staking parameter. The old consensus allowlist remains
Ed25519 until a separate coordinated governance update.

SDK55 removes textual signing; the chain CLI retains supported direct and
Amino signing. The new optional BlockSTM executor is wired through the standard
SDK helper. Sequential execution remains the default. New unrelated modules
and optional economic changes are not implicitly enabled by this migration.
Unordered transactions retain Dungeon's existing disabled configuration.

## Preserved Dungeon modules

Tokenfactory, globalfee, Hyperlane mailbox/ISM/warp, and historical group
functionality retain their public messages, store keys and existing data.
Their SDK55 compatibility sources are tracked under `third_party/`, with
upstream versions, module ZIP identities and licenses. The open-source SDK53
group implementation is retained rather than replacing it with the Enterprise
package. Removed group/params API descriptors are preserved in `compatapi`.

Legacy params and capability stores remain mounted for historical state and
compatibility. Modern SDK/IBC parameter keepers no longer depend on them.
The removed SDK baseapp legacy-consensus helper is preserved locally for
historical Dungeon upgrade handlers. No stores are silently deleted.
The historic localhost client decoder from the v11 compatibility work also
remains, including the public-record regression fixture.

PFM's 3-to-4 migration rejects any old nonrefundable in-flight packet. Such
packets must be settled before the upgrade; do not weaken the refusal.
Rate limiting's official 1-to-2 migration clears legacy pending markers that
lack a denom. Existing quotas and charged flow survive; that flow remains
charged until the quota window resets. Settle pending transfers beforehand
where practical. This is an upstream migration behavior, not a byte-for-byte
preservation promise for those markers.

## Build and local verification

From Linux amd64 with Go1.27.1, curl, musl-tools and GCC11:

```sh
go test -mod=readonly -count=1 -tags pebbledb,ledger,test_ledger_mock ./...
bash scripts/test_v12_ports.sh
bash scripts/build_v12_release.sh
```

The builder verifies the official WasmVM3.0.8 musl archive SHA256, checks that
the binary is static, checks its actual runtime library version, and creates
a tarball with source/provenance and checksums under `build/v12-release/`.
Final native release builds require a clean checkout. Source archives/Docker
contexts require an explicit full source commit; their provenance records
that checkout cleanliness was not verified. Never treat that as clean-source
proof. The candidate package for validator rehearsal should come from the
clean native builder. Only Linux amd64 packaging is verified locally.

The baseline must be exact v10 tag commit
`281010e4445cd2f478ed39b397926ce221e22c06`, built with Go1.25.14. Then:

```sh
export BINARY_V10=/absolute/path/to/exact-v10/dungeond
export BINARY_V12="$PWD/build/v12-release/dungeond"
export CW20_WASM=/absolute/path/to/wasmd-v0.60.9/benchmarks/testdata/cw20_base.wasm
DB_BACKEND=pebbledb bash scripts/test_v12_upgrade.sh
DB_BACKEND=goleveldb bash scripts/test_v12_upgrade.sh
bash scripts/test_v12_quantum.sh
```

Scripts create private fresh fixture homes and terminate only their own child
nodes. They never touch production services, homes or keys. Logs deliberately
exclude generated private-key/mnemonic files. The quantum script replaces a
fresh local fixture's signer with another freshly generated key and fresh
sign-state; **that operation is not a production key-rotation procedure**.

The governance rehearsal checks committed execution, not only simulation or
mempool admission: pre-upgrade CW20 state/transfer, factory balances and mint/
burn, Hyperlane mailbox/warp, group records, account/staking/rewards/authz/
feegrant/globalfee, historical queries, fee rejection and restart. Additional
tests cover ML-DSA authentication/replay/corruption, rotation/history/slashing/
fee burning, module-parameter guards, PFM migration refusal, retained rate-limit
flow, IBC transfer/ack/return, three-chain forwarding with quota rejection and
source refunds, and IBC v2 transfers with rate limiting.

The Docker interchain suite uses a separate SDK50 client-harness module; this
does not choose the chain binary's dependencies. Its retired Actions versions
and Sonic/Go27 compatibility pins are updated. Old ICS consumer setup is replaced
with standard IBC links because Dungeon is a standalone chain. Native suite
compilation is a separate check; Docker execution requires a Docker runner.

## Production rollout gates

Before picking a height: rehearse a current mainnet snapshot/export and every
active IBC route, bridge delivery and live contract integration; inspect pending
PFM/rate-limit packets; review the local ports; stage the exact clean candidate
on a multi-validator test network with the real signer software. Prove state
sync/snapshots and recovery from a backup of the old database. A synthetic
genesis rehearsal is not a mainnet-state rehearsal, and a fixture signer
restart is not proof of remote-signer compatibility.

Coordinate a software-upgrade proposal named `v12` with all validators and
publish its exact binary/source checksums. The software upgrade alone keeps
existing validators signing with Ed25519. Do not rotate production consensus
keys as part of installing this binary.

Before consensus activation, all relevant IBC counterparties and relayers must
verify the new ML-DSA headers. Upgrade counterparties first or their clients can
stop accepting Dungeon headers. After that, approve the consensus allowlist
update through governance, generate and secure each new validator key, and use
the staking `rotate-cons-pub-key` transaction with a signer handoff at the
SDK/Comet activation height. Keep old-key signing/evidence records; do not reset
or reuse production signing state. Rotate validators gradually and verify
quorum, liveness, slashing tracking and IBC delivery after every change.

Wallets, hardware devices, explorers and bridge systems require compatibility
testing and any necessary app releases. Existing account keys do not become
quantum resistant automatically; users adopt new ML-DSA accounts and move assets
when their wallet supports them. Historical signatures remain historical.
There is no planned mainnet rollback after migration: recovery requires the
pre-upgrade backup and coordinated network action, not starting v10 on a
migrated store.
